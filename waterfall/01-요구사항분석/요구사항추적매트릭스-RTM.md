## 1. 목적

요구사항이 기획·정책에서 나와 설계·구현·테스트까지 빠짐없이 이어지는지 추적한다. 요구사항이 바뀌면 영향받는 설계·코드·테스트를 이 표로 찾는다.

---

## 2. 추적 범위

[서비스 기획서](../00-기획/서비스기획서.md) v1.1의 MVP-001~008과 [비즈니스 정책서](../00-기획/비즈니스정책서.md) v1.1의 규칙을 [SRS](요구사항명세서-SRS.md)의 FR·NFR에 연결한다. 제외 항목(P4: FR-018, FR-019)은 추적 대상에서 뺀다. UC는 [유스케이스 명세서](유스케이스명세서.md) 1.0을 따른다.

## 3. 상태 정의

### 3.1 요구사항 상태

| 상태 | 설명 |
|------|------|
| 초안 (Draft) | 최초 작성 상태, 검토 필요 |

| 상태 | 설명 |

| N/A | 해당 단계가 적용되지 않음 |

### 7.2 미매핑 항목 관리 규칙

1. 미결 항목마다 사유, 담당자, 해결 기한을 기록한다.
2. 단계 검토에서 남은 미결 항목이 다음 단계에 미치는 영향을 확인한다.
3. 승인된 요구사항이 바뀌면 변경 요청을 연결하고 관련 설계·구현·테스트를 함께 갱신한다.

| 단계 전환 | RTM 확인 항목 |
| --- | --- |
| G1 요구사항 → 시스템 설계 | 승인 범위의 요구사항 행에 출처와 SRS 수용 기준이 있다. (충족: 6장 출처 연결률·수용 기준 정의율 100%) |
| G2 시스템 설계 → 상세 설계 | 시스템 수준에서 적용되는 설계 결정·자료를 연결한다. |
| G3 상세 설계 → 구현 | 구현 대상에 상세 설계 또는 대응 작업 참조를 연결한다. (FR 17개 모두 상세설계 절 연결) |
| G4 구현 → 테스트 | 테스트 대상 요구사항에 구현 참조와 수용 기준에 맞춘 TC를 연결하고 후보 빌드를 기록한다. |
| G5 테스트 → 배포 | 대상 빌드의 테스트 판정과 증빙, 허용된 제외 결정과 승인 기록을 연결한다. |

단계별 승인과 예외 처리 기준은 [검토 체크리스트](../08-검토/단계별검토-체크리스트.md)에서 확인한다.

## 8. RTM 갱신 절차

### 8.1 갱신 주기

1인 프로젝트이므로 모든 갱신은 프로젝트 담당자(임지영)가 하고, Claude가 초안을 작성한다.

| 이벤트 | 갱신 항목 |
|--------|----------|
| 요구사항 추가/변경/삭제 | 요구사항 ID, 상태 열 |
| 유스케이스 작성/변경 | UC 열 |
| 설계 문서 작성/변경 | 설계 참조 열 |
| 코드 구현 완료 | 구현 참조 열, 구현 상태 |
| 테스트 실행 완료 | 테스트 상태 |
| 단계 게이트 검토 | 커버리지 요약 |

### 8.2 변경 영향 분석 체크리스트

요구사항 변경 시 다음 항목을 점검한다:

- [ ] 변경된 요구사항의 RTM 상태 업데이트
- [ ] 관련 유스케이스 영향 확인 및 갱신 여부 판단
- [ ] 관련 설계 문서 영향 확인 및 갱신 여부 판단
- [ ] 관련 구현 모듈 영향 확인 및 수정 범위 산정
- [ ] 관련 테스트케이스 영향 확인 및 추가/수정 여부 판단
- [ ] 연관 요구사항(의존성)에 대한 파급 효과 확인
- [ ] 커버리지 요약 재계산
